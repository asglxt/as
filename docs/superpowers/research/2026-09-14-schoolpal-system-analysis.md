## 1. 技术栈观察

- 前端：Vue 2.6.11 + Vue Router 3.0.1，SPA；按路由分块加载。
- UI/组件：Ant Design 图标、FullCalendar 4（日历/排课）、TinyMCE 5（富文本）、Video.js、ECharts 4（报表图表）。
- 工具库：moment、Intl、JSZip、Ali OSS SDK、jQuery（历史遗留）。
- 静态资源：CDN（cdn.schoolpal.cn），前端版本 erp-lego-web-static-fe/131/17155。
- 接口风格：REST，主前缀 /api 与 /api2，按领域分组（Org/Class/User/Order/Common/Desktop/StuInfo...）。
- 版本：页面显示 v13.0。

对我们自建系统的启示：校宝是典型“单体 SPA + REST + 多模块中台”结构，按业务中心划分前端路由与后端领域服务；我们现有的 React + Fastify + PostgreSQL 结构方向一致，不需要推倒重来，重点是补齐领域模型。

## 5. 数据模型推断（用于自建系统）

从路由与接口可以还原出校宝的核心实体关系：

    机构 Org
     ├── 校区 School（多校区）
     ├── 部门 Department ── 员工 Employee ── 角色 Role/权限 Jurisdiction
     ├── 课程 Lesson（收费模式、课程价格、科目、年级）
     │    └── 班级 Class（满班人数、授课教师、校区、状态）
     │         ├── 学员 Student（档案、年级、扩展字段、状态）
     │         ├── 排课 Schedule（时间、教师、教室、冲突检测）
     │         ├── 考勤 Attendance / 教学日志 TeachingLog（签到、补课、试听）
     │         ├── 点评 Comment（评分、评语）
     │         └── 作业 Homework（布置、提交、批改）
     ├── 考试 Exam ── 考试项 ExamItem ── 成绩 ExamScore（按学员）
     ├── 订单 Order（报名、续费、转班、退费、补贴、积分、物料）
     │    └── 收款账户/对账 Account/Settle
     ├── 合同 Contract（模板、印章、电子合同）
     └── 报表 Report（经营、财务、教务、招生）

关键设计点：

1. 课程与班级分离：课程是产品（价格、收费模式），班级是课程的具体开班。
2. 考试与考试项分离：一场考试包含多个考试项（科目/维度），成绩按“学员 × 考试项”存储，因此支持分项成绩、总分、排名。
3. 班级席位与学员关系独立：支持分班、转班、旁听、补课、一对一。
4. 排课有冲突检测：创建/修改排课时校验教师、教室、学员时间冲突。
5. 权限是“角色 + 模块 + 校区”的组合，且左侧导航由服务端下发（GetLeftNavigation），未授权模块直接无权限提示。
6. 大量明细报表：所有经营指标都可以下钻到班级/学员/订单明细。

2. 排课（Schedule）与班级席位：课表、冲突检测、补课/试听、一对一。

6. 订单/财务：报名、续费、转班、退费、收据、对账、电子合同。
7. 报表中心：经营/财务/教务/招生报表与下钻明细。

## 9. 权限机制的关键发现（补充）

- 前端路由不是静态注册：app.js 中先按当前用户的 `currentUser.Authority` 过滤路由，再 `addRoutes`：
  - `new VueRouter({ mode: "history", base: "/web/" })`
  - 过滤条件：`meta.viewAuthority` 与用户 Authority 取交集，无交集的路由被移除。
- 被移除的路由访问时会落到“无权限访问”页，因此直接改 URL 无法绕过。
- 工作台（/web/desktop）的 `viewAuthority` 是空数组，所以任何账号都能进入；招生/办理/教务/教学/报表/内部管理等路由都带有权限码。
- 工作台还提示“当前机构未认证，请尽快认证保证系统使用权益”，机构未认证可能同时限制了模块可用性。
- 结论：需要确认两件事
  1. 当前账号在“内部管理 → 角色权限”里是否被授予了这些模块的权限码。
  2. 机构是否已完成认证/模块开通（未认证机构可能只开放工作台）。

- 统计：共计 N 个班级 | N 个班级正在开班；共计在读学员 N 名 | 共计在读人次 N 个。

- 表格字段：学员姓名、关系、联系方式、项目、成绩、来源、考试日期、考试、班级名称、备注、操作。
- 实测为空数据（该机构近期没有录入成绩）。

这是对成绩模型最关键的确认：
- 一条成绩记录 = 学员 + 项目 + 成绩 + 来源 + 考试日期 + 考试 + 班级 + 备注。
- 「项目」是考试成绩的分项维度（等价于我们方案里的 ExamItem）。
- 「考试设置」和「项目设置」是两套独立配置：先配置考试与项目，再录入学员成绩。
- 「来源」用于区分成绩从哪里来（例如教师录入、报名成绩、导入等）。

开发结论：我们一期把成绩建成“一场考试一个分数”是不够的，二期必须升级为：
1. 考试 Exam（考试名称/日期/班级/备注）
2. 考试项 Item（项目名称/满分/排序/是否计入总分）
3. 成绩 Score（学员 × 考试项 × 分数/等级/评语/来源）

### 10.14 校宝成绩模型的最终确认

校宝的学员成绩记录字段：学员姓名、关系、联系方式、项目、成绩、来源、考试日期、考试、班级名称、备注。

对应我们二期应落地的表结构：

    exam_projects (id, name, enabled, sort)
    exams         (id, name, enabled, sort)
    student_scores(
      id,
      student_id,
      project_id,      -- 项目字典
      exam_id,         -- 考试字典
      class_id,        -- 班级
      score,           -- 成绩值（分数或等级）
      source,          -- 来源（教师录入/导入/报名成绩等）

这比我们一期“一场考试一个分数”的表结构更贴合真实业务：考试是字典、项目是字典，成绩是“学员 × 项目 × 考试”的记录。

### 10.22 内部管理 / 角色权限页（实测，2026-09-14）

- 权限粒度是「模块级」（还没有到按钮/字段级）。
- 这份权限清单同时也是校宝的完整模块清单（31 个模块）。
